# 检查回执恢复：本阶段实现与交接

本阶段以 main `a3ab69b674705760a9b62e9cd00c130f53c5b686` 为基线，完成阶段计划中的最高优先级缺口：检查命令已执行、ledger 并发追加被拒后，显式恢复已保存的回执关联。原项目现有改动保留在原工作区，全部实现位于隔离分支。

## 已完成行为

- 新回执使用独立恢复版本，保存稳定 check ID、Case/Run/Plan、proposal SHA 和原 ledger 字节前缀。原 SHA 从写入前的序列化字节计算，冲突错误打印原值。
- `recover-plan-check` 要求原 SHA，可先 dry-run；不执行保存的 argv。复用既有三节点/六关系，并在原 append lock 内重新核对 sequence、ledger SHA、回执/输出和仓库观察。
- 已完整记录时幂等返回，ledger 字节不变。缺失关系、冲突归属、错误 Run 或混合来源明确拒绝。
- 按原始历史逐次合并回执身份，阻止旧成功覆盖后来记录/更新的失败或无效证据；身份后来改走也不绕过门禁。
- 合法失败或过期回执可恢复为历史，审阅保持 failed/stale。旧已关联回执继续可读；缺绑定的旧孤立回执不自动导入。
- ledger、lock、实际 receipt/output 均须在 ignored `.artifacts`，包含精确例外或已跟踪文件时拒绝。MCP 仍是原六个只读工具，可审阅恢复结果。

## 后续决策与人工任务

本里程碑没有实现 proposal 到 runtime-managed Task 的执行桥接，也没有新增 Approval 或 MCP 写工具。业务验收由谁确认、何时允许执行及是否允许 MCP 写入，仍需产品决策；这些不阻塞本次恢复机制合入。旧孤立回执需要人工审阅。主机插件安装体验、历史 UI、人类业务验收、GPU/Android/设备验证未在本阶段执行。
